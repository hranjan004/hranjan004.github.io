Microgrid Manager

Residential energy management · UCSC capstone and continued development

A home energy meter can tell you how much power you’re using. Our UCSC capstone set out to make that data useful: show it live and estimate which appliances are running. Working with Dr. Pat Mantey and AnyLog, I built the data and inference path using Kafka, PostgreSQL, PyTorch and ONNX, then packaged the services in Docker for the residential deployment.

I spent much of the project making the pieces work together. When thousands of readings stopped short of the database, I traced the problem to AnyLog’s cluster registration. When appliance labels said a heat pump was always off, I audited the data and rebuilt the labeling rules. The system now brings together live dashboards and local inference across three panels; I’m continuing to improve how we validate appliance predictions.

Engineering details

For non-intrusive load monitoring, I audited the labels before training. The original label stream marked the heat pump OFF in all 3,433 sampled windows, including high-load periods. I built physics-informed rules using power thresholds and temporal behavior, then used PyTorch BiLSTMs and ONNX for local inference across HVAC, water-heater and kitchen panels. For mixed kitchen loads, I separated sustained baseline changes, compressor oscillations, discrete events and paired pulses so one detector did not have to explain every load shape.

I extended the inference rules to prefer measured PV and battery snapshots over weather estimates, with a fallback when telemetry is missing. A regression test caught Python’s truthiness turning 0% cloud cover into 100% overcast. I replaced the fallback with an explicit missing-value check. All 11 solar-path tests passed locally and inside the deployed inference container, including a real-ONNX disaggregation cycle with a synthetic solar snapshot; the existing 17 application tests also passed locally.

Experimental model development

I tested a MATNilm model with input perturbations and found that its predictions barely changed. The original targets apportioned panel power using the same rules the model was supposed to learn. I rebuilt the experimental training path around two measured appliance targets, masked state supervision for unmeasured heads, an energy-balance loss and a residual-power head. I also made ambiguous rules abstain during strong 240 V events instead of manufacturing labels.

In the recorded retraining experiment, maximum probability shifts under input perturbation increased from 0.0004 to 0.3818 on Panel 1 and 0.8134 on Panel 2. That demonstrated input responsiveness, not generalization. The measured test events were limited and Panel 3 training remained incomplete, so I kept this work separate from the deployed BiLSTM path.

HTTP / HTTPS forward proxy

Concurrent networking and cache design in C

I built this C proxy to get closer to what happens between a browser and a server. It handles concurrent clients with POSIX threads and reuses complete HTTP responses through a shared cache. I implemented FIFO and LRU on the same linked-list structure so I could compare how insertion order and recent use affect eviction.

The interesting part was deciding what was safe to reuse. I limited cached responses to 1 MB, kept incomplete responses out of the cache, and protected shared state with a mutex. For HTTPS, I added CONNECT tunneling so encrypted traffic passes between the client and origin without the proxy decrypting it.

Engineering details

For HTTPS, I implemented CONNECT tunneling: the proxy opens a TCP connection to the destination and relays encrypted bytes in both directions. TLS stays end to end between client and origin, so the proxy does not terminate TLS or cache the encrypted response as HTTP content. The thread-per-connection design keeps connection handling straightforward; a bounded worker pool is a separate design for controlling concurrency.

Osmosis

FPGA game · CSE 100L, UC Santa Cruz

I built a game in which eight moving molecules have to be separated by color before the timer runs out. It runs on a Basys3 FPGA and a VGA display. Using structural Verilog, I built the display timing, movement, collisions and game controller as hardware modules.

One bug taught me more than a clean simulation could: the molecules all appeared at the origin because reset finished before their clock started. I fixed the initialization in the FPGA flip-flops, then rendered a frame to check what the player would actually see. I also added randomized positions, speeds and directions and used focused Icarus Verilog tests to check the display and game logic.

Engineering details

Full-game simulation was expensive with the clock primitives and continuously toggling LFSR. I used Icarus Verilog with behavioral primitive stubs, a directly driven pixel clock for VGA checks, and accelerated frame pulses for game-logic tests. Rendering an idle frame to a bitmap exposed placement errors that passing sync and FSM tests had missed.

GPT-2 CPU performance analysis

Computer architecture · UC San Diego summer session

I wanted to understand where a GPT-2 training loop was spending its CPU time before trying to make it faster. Linux perf showed that matrix multiplication dominated the work, with the backward pass alone accounting for about a third of sampled cycles.

I used cache tiling to reuse data and AVX2 intrinsics to process several values per instruction, without changing the test drivers or adding libraries. The follow-up profiling put the L1 data-cache miss rate at roughly 2–3%, down from about 9%. It gave me a concrete way to connect a code change with what the processor was doing.

Engineering details

I also studied OpenMP thread scaling against Amdahl’s law, TLB behavior across page sizes and NUMA locality. The work taught me to separate kernel-level improvements from whole-program speedup and to use hardware counters to explain where an optimization helped.

Two-player Quick Add

Structural RTL game controller · Basys3 FPGA

I turned a single-player arithmetic game into a two-player FPGA game. I used a nine-state controller and synchronized, latched button inputs so both players could answer within the same time window and the game could resolve a win, loss or tie.

The trickiest bug happened when a player reached zero points: the score changed one clock cycle too late for the controller to stop the next round. I traced the state transitions and added the missing game-over checks. Both Icarus Verilog testbenches passed afterward, including ties, simultaneous wrong answers and game-over lockout.

Engineering details

I checked the fix with a focused state trace, then ran both verification testbenches in Icarus Verilog. The recorded scenarios passed for solo wins and losses, ties, both players losing, neither player pressing, game-over lockout and the debug switch modes.
