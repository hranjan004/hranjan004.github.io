Debugging a pipeline that looked empty

Field notes on partition discovery, REST request context and timestamp handling in our AnyLog deployment.

THE QUESTIONIs the data missing, or is the query looking in the wrong place?

Deployment-specific observations from my archived project records. Request behavior varies with runtime and routing context; these notes are not universal AnyLog configuration instructions.

An empty query result did not always mean that ingestion had stopped. In our deployment, readings lived in discovered partition tables while a parent-table query could return nothing. Checking the actual tables and time window was more useful than immediately restarting the pipeline.

REST behavior also depended on request context. Missing the expected AnyLog user-agent header and mixing client-command syntax with REST headers caused failures. Host-side and container-side routing differed, so I learned to test a minimal query in the same runtime as the failing service.

Timestamp handling was another boundary to check explicitly. Event time and database ingestion time were different fields. A serialization change could turn a valid reading into a quarantined row; accepted formats had to be verified against the deployed ingestion path.

I also encountered channel-name predicates that failed where fetching a bounded time window and filtering in the client worked. That workaround needed a clear bound so a query fix did not become an unbounded data transfer.

My debugging order became: confirm recent data in the right partition, reduce the REST request to a minimal query, verify routing context, then check timestamps at each boundary. These steps separated missing data from a query or serialization failure without exposing household deployment details.
