The opportunity

A solar home produces continuous telemetry. Its operator needs a clearer answer: which appliances are running, how the energy system is behaving and what to do next. I led the UCSC capstone that brought those readings into a local inference and monitoring system.

What I engineered

As lead engineer, I designed and trained three two-layer PyTorch BiLSTMs with appliance-specific heads and weighted loss. Physics-informed labeling captured sustained loads, compressor cycles, high-power events and paired pulse patterns.

I engineered the deployment contract around each ONNX model: feature normalization, appliance names and thresholds travel with the graph. Independent output probabilities allow several appliances to run at once.

I connected Kafka and MQTT telemetry through three EdgeLake / AnyLog nodes and PostgreSQL to ONNX inference, FastAPI and React dashboards. Load, Generation, Storage and Decision Support organize the system around the operator’s decisions.

I coordinated model, labeling and dashboard delivery with weekly sponsor reviews, working with Dr. Pat Mantey and the AnyLog team on infrastructure.

The results

The BiLSTM work achieved 0.932 heat-pump F1 on held-out physics-labeled data.

The distributed pipeline handles roughly 960 messages/min across three nodes. The published LF Edge report records single-digit milliseconds of CPU inference per panel, with predictions written every 30 seconds.

Delivered local inference across three panels and a residential monitoring dashboard; completed the capstone in October 2026. All 11 solar-path tests passed locally and inside the deployed inference container.

Co-authored the LF Edge article documenting the residential edge-intelligence system.

Why it matters

The product is the complete path from a meter reading to a useful decision. Explicit model contracts, local inference and clear service boundaries make that path maintainable.

Engineering decisions & measurement context

Model outputs are independent appliance probabilities, allowing multiple loads to be ON at once. Physics-informed rules add temporal and power constraints; ambiguous windows are excluded instead of forced into training labels.

A model deployment couples the ONNX graph with feature normalization, appliance names and thresholds. Checking those contracts prevents a numerically valid output vector from being interpreted against the wrong labels.

Kafka / MQTT → EdgeLake / AnyLog → PostgreSQL → ONNX + rules → FastAPI → dashboard. I kept the interface and inference layers separate so a GUI change did not create a second model runtime.

The deployment runs as roughly 11 Docker containers, brought up with a single docker compose command. Keeping ingestion, inference, storage and presentation services separate makes the operational boundaries explicit.

The Ask feature connects a local model through Ollama to an MCP client exposing 18 tools. It gives the dashboard a natural-language interface while keeping the local inference path separate from language-model responses.

Evaluation scope: 0.932 heat-pump F1 is measured against held-out physics-derived labels. Only two of 22 appliance outputs had independent measurement in the capstone; automated appliance control was outside its completed scope.
