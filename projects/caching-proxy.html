The problem

Repeated HTTP requests can duplicate origin work, while concurrent clients introduce shared-state hazards. I built a proxy to explore both response reuse and the correctness of network handling.

How I approached it

I implemented FIFO and LRU eviction with a shared cache, keyed by the requested resource. Cache updates are synchronized, and incomplete or oversized responses are excluded.

The documented detached-thread variant uses POSIX threads for clients and CONNECT tunneling for HTTPS, relaying encrypted bytes without terminating the client’s TLS session.

A separate thread-pool variant explored bounded work queues and clean shutdown. I keep those designs distinct when discussing their concurrency behavior.

What changed

Reduced cached response time by 50% in my cached-response benchmark.

Built HTTP response caching with a 1 MB per-response bound and HTTPS CONNECT forwarding.

I exercised argument validation, cache-policy sequences, response-body checks, sanitizer runs and concurrent-request exercises.

What I took from it

I learned to treat caching as a correctness problem before treating it as a speed optimization. The 50% improvement applies to my cached-response benchmark; response boundaries, cache policy and concurrent access determine whether that improvement is useful.

Engineering decisions

A cache entry is reusable only when the full HTTP response is available and within the size bound. A mutex protects shared cache mutation; the linked-list order implements FIFO insertion order or LRU recency.

HTTPS CONNECT is a bidirectional byte tunnel in the documented variant. TLS remains between client and origin, so the proxy cannot treat the encrypted payload as an ordinary cacheable HTTP response.
