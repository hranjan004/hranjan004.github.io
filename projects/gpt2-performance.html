The opportunity

Matrix multiplication dominated the CPU training loop. I used hardware counters to choose where to optimize, then improved the memory access and arithmetic inside those kernels.

What I engineered

Linux perf attributed 33.09% of sampled cycles to backward matrix multiplication and 23.88% to forward multiplication, setting the optimization priorities.

I tiled the computation for data reuse and used AVX2 fused multiply-add instructions to process eight floats at a time within the existing build constraints.

Related experiments examined thread scaling, page sizes and NUMA locality to connect code changes with processor behavior.

The results

Reduced the hot kernel’s L1 data-cache miss rate from 9.17% to approximately 2–3% in follow-up profiling.

Implemented cache tiling and vectorized matrix arithmetic, using hardware counters to evaluate the changes.

Why it matters

Profile the expensive work, improve locality, then vectorize. Separate measurements make it possible to connect an optimization to the behavior it actually changes.

Engineering decisions & measurement context

The optimization targets memory reuse inside matrix multiplication. Tiling changes the working set; AVX2 changes the arithmetic issued per instruction. These mechanisms need separate measurements because lower cache-miss rates alone do not establish total speedup.

Compiler flags, matrix dimensions and thread settings need to stay fixed when comparing kernel changes. I used hardware counters to connect the observed cache-miss reduction to the memory-access changes.

My optimization work focuses on matmul_forward and matmul_backward and their pthread helpers. Integration had to stay within an existing notebook build, without adding compiler flags or external libraries.
