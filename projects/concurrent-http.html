The problem

Concurrent clients can read and overwrite the same file. A server needs to parse partial network input correctly and coordinate file access so its responses and audit log tell a consistent story.

How I approached it

I developed the server from a single-connection GET / PUT implementation into a concurrent design. The work covered request-line validation, header parsing, content lengths, response codes and cleanup of sockets and file descriptors.

I worked through worker dispatch, per-resource reader–writer locking and serialized audit logging. Debugging crossed several boundaries: listener APIs, partial reads, malformed requests and differences between local and submission builds.

What changed

Implemented the HTTP file-server coursework and documented the progression from protocol parsing to concurrent request handling.

The software work also provides the behavioral starting point for my separate FPGA HTTP experiment.

What I took from it

The project connects protocol parsing to resource ownership. A request is only handled correctly when parsing, file access, response construction and cleanup remain consistent under concurrent work.

Engineering decisions

A successful socket read can return only part of a request. The parser must preserve bytes already received after the header terminator and account for the remaining body before completing a PUT.

File locking and audit ordering are separate correctness concerns. Protecting file contents does not automatically make the log reflect the same operation order.
