The problem

A small file utility still has to distinguish command metadata from payload bytes, handle failed system calls and avoid assuming that one read or write transfers everything.

How I approached it

I worked on a memory.c utility that reads get and set commands from standard input and maps them to file reads or replacements.

The implementation and review covered command parsing, declared payload length, file-opening flags, error messages and releasing allocated buffers and descriptors.

What changed

Built the file-I/O coursework foundation used later in HTTP request handling.

The project made byte counts, input boundaries and cleanup explicit parts of the interface.

What I took from it

This work taught me to keep byte counts, boundaries and cleanup visible. Those details became the foundation for handling HTTP request bodies and files later.

Engineering decisions

Text tokenization is appropriate for command fields, but payloads require byte-counted handling. The review exposed why treating the whole input as a null-terminated string is fragile.
