The problem

A microcontroller game needs to respond to hardware events while keeping game state consistent.

How I approached it

I organized Battleship-style gameplay as state machines and used timers, hardware interrupts and low-level peripheral drivers to connect software behavior to the board.

My implementation connects an Agent state machine to message parsing, negotiation, field state and OLED rendering. UART and circular-buffer modules carry the board-to-board message path.

What changed

Implemented the embedded game in C, building experience with event-driven C and hardware interfaces.

What I took from it

Working with physical inputs made event handling concrete. I had to think about how the game responds to a sequence of events, not just whether a function produces the right answer in isolation.

Engineering decisions

Timers and hardware interrupts supply events to the game state machines. Peripheral access and application state need clear boundaries so a hardware event produces one consistent state transition.

Separating negotiation, field updates and message events makes turn-taking explicit. The agent owns the transition between negotiation, attack, wait and end-game behavior while the display reflects that state.
